# Phase 3 구현 및 검증 기록

검증일: 2026-10-30. 실제 회사 데이터와 운영 DB를 사용하지 않고 가상 데이터로 검증했다.

## 적용 방법

Phase 2까지 적용된 Supabase DB에는 다음 파일을 순서대로 추가한다.

1. `supabase/migrations/20261030000200_stock_transactions.sql`
2. `supabase/migrations/20261030000300_cleaning_fifo.sql`
3. `supabase/migrations/20261030000400_bom_planning.sql`

002를 이미 적용했다면 003과 004만 추가한다. SQL Editor에서는 각 파일 전체를 새 쿼리에서 한 번씩 실행한다. 이전 migration을 다시 실행할 필요가 없다. CLI를 쓰는 프로젝트는 기존 migration 이력을 확인한 후 `supabase db push`로 추가한다.

이 migration들은 기존 현재고를 유지하고 반납 보류 수량을 0으로 추가한다. 기존 거래의 용도는 GENERAL로 초기화한다. 과거 Excel 사용 이력을 추정하거나 다시 적재하지 않는다. 새 화면과 API를 사용하려면 앱 코드와 DB migration을 모두 적용해야 한다. 이번 개발에서는 연결된 실제 Supabase 프로젝트에 SQL을 실행하거나 앱을 배포하지 않았다.

## 구현 내용

- `/receipts`: 원료·기존/신규 제조 LOT·위치·수량·시험번호 입력. 실제 입고건과 시험대기 재고를 함께 생성한다.
- `/issues`: 원료와 수량에 따라 FIFO를 미리 보고 실제 불출한다. 입고일 → 등록시각 → 입고건 ID → 위치 ID 순서이며 창고 지정은 선택이다. 부족하면 모든 차감을 취소한다.
- `/boms`: 관리자가 기준 생산 1회분의 BOM 원료·수량·단위·일반/세척 용도를 등록·변경한다. 단위 호환·밀도와 세척 18L 배수를 검사한다.
- `/production`: 작업자·관리자가 BOM·생산일정·생산 배수를 등록한다. 미출고 예정만 자동 갱신하고 출고 완료분·수기 추가 불출은 보존한다. 실제 불출 확정에서 재고 차감·원장 연결·계획 완료를 함께 처리한다.
- `/returns`: 원불출의 분할행을 찾아 반납한다. 반납량은 이미 반납한 수량을 제외한 범위로 제한되며 보류 재고가 된다. Admin이 확인 사유를 남겨 전체 또는 일부를 승인한다.
- `/transactions`: 원료·입고건·현재/과거 시험번호·거래유형·기간으로 검색한다. 날짜순 내역, 위치별 전후 잔량, 거래 당시 시험번호, 제조 배치, 담당자·사유·비고와 묶음 거래 상세를 제공한다.
- 재고 조회에 반납 보류를 반영하고, 원료 상세의 입고건에서 해당 원장으로 이동한다. 최근 거래도 대시보드에 연결했다.

세척은 입고건별 가용량에서 18L씩 배정한다. 25L·100L에서 36L를 출고하면 18L씩 차감하고 앞의 7L를 남긴다. 같은 제조 LOT여도 서로 다른 입고건의 잔량을 합치지 않으며, 동일 입고건의 여러 위치는 선택 창고 범위에서 합산한다.

입고·불출은 기본단위 변환과 등록 밀도를 적용하고 최종 수량을 소수 6자리로 반올림한다. 입력수량·단위·밀도를 보존한다. 반납·승인은 기본단위로만 입력한다. 기한 미확인·경과, 부적합·시험대기·보류, 비활성 원료/창고/위치는 불출에서 제외한다. 예약 및 반납 보류 수량도 제외한다.

RPC는 실제 사용자와 권한을 검사한 후 같은 트랜잭션 안에서 잠금·잔고 변경·거래 기록을 수행한다. 같은 요청키로 재시도하면 기존 결과를 반환하며 다른 입력의 키 재사용은 거절한다. 원장 수정·삭제와 잔고 직접 변경은 관리자 계정에도 허용하지 않는다.

## 자동 검증

| 검증 | 결과 |
| --- | --- |
| Nuxt TypeScript 검사 | 통과 |
| Vitest 단위·UI 상태·DB 테스트 | 11개 파일, 354개 통과 |
| 프로덕션 빌드 | 통과 |
| 빌드된 앱 HTTP 통합 테스트 | 18개 통과 |
| PostgreSQL 17 독립 연결 경합 | 8개 통과 |
| `git diff --check` | 통과 |

로컬 pnpm의 실행 전 의존성 검사에서 재설치 확인을 요구하여 의존성은 바꾸지 않고 이미 설치된 실행 파일로 검사했다.

```sh
node node_modules/nuxt/bin/nuxt.mjs typecheck
node node_modules/vitest/vitest.mjs run
node node_modules/nuxt/bin/nuxt.mjs build
node --test tests/integration/*.test.mjs
node --test tests/integration-postgres/transactions.test.mjs
```

DB 검증은 실제 migration을 PGlite PostgreSQL 엔진에 적용한다. HTTP 검증은 실제 Nuxt 서버와 Supabase 클라이언트를 실행하고 Auth/PostgREST만 가상 서비스로 대체한다. 실제 Supabase Cloud의 연결 검증은 포함하지 않는다.

경합 검증은 로컬 Docker `postgres:17-alpine`의 전용 컨테이너에서 독립 psql 연결을 실행한다. 외부 네트워크·공개 포트·영구 데이터 볼륨 없이 실행하고 생성한 컨테이너만 정리한다. 두 연결의 실제 잠금 대기를 확인한 뒤 진행하여 다음을 검증했다.

1. 합계가 가용재고를 넘는 동시 불출에서 한 요청만 성공하고 실패 요청의 부분 차감·이력은 남지 않는다.
2. 같은 요청키의 동시 재시도는 한 번만 반영한다.
3. QC 보류 변경과 경합한 불출은 새 품질상태를 반영하여 거절한다.
4. 원불출량을 넘는 동시 반납에서 한 요청만 성공하며 현재고와 보류 수량이 일치한다.
5. 세척 동시 불출은 18L 배수만 배정하고 동일 입고건의 남은 7L를 보존한다.
6. 세척 불출과 QC 변경의 경합에서 변경된 품질상태를 반영한다.
7. 일정 변경이 먼저 잠금을 잡으면 오래된 revision의 출고 요청을 거절한다.
8. 계획 출고가 먼저 잠금을 잡으면 뒤따른 일정 변경이 출고 완료 계획을 보존한다.

추가 DB·HTTP 검증은 계획 생성 시 재고 불변, 일정 취소·재활성화, 출고 완료 항목의 비활성/밀도 변경 후에도 미출고 항목만 재계산, 동일 요청 재시도, BOM 단위 호환과 원료 참조 삭제 방지, 역할별 권한을 포함한다.

## 브라우저 검증

가상 관리자 계정으로 별도 로컬 앱에서 확인했다.

- 100kg 불출 미리보기가 시험번호 2개에 60kg·40kg으로 배분되고, 저장 후 예약 10kg을 남긴 실제 잔량이 원장과 일치했다.
- 원불출에서 3kg 반납 후 보류 상태를 확인하고 2kg만 승인하여 대기 목록에 1kg이 남았다. 승인 시 현재고는 그대로였다.
- 신규 제조 LOT를 포함해 12.345678kg을 입고하고 시험대기 안내와 원장의 소수 6자리 수량을 확인했다.
- 원장에 불출·반납·부분 승인·입고의 전후 잔량, 시험번호, 제조 배치, 사유가 표시되었다.

세척·BOM 확장도 별도 가상 서버에서 실제 브라우저로 확인했다.

- Admin이 세척 18L BOM을 등록하고 생산 배수 2로 36L 예정을 생성했다. 일정을 배수 3으로 변경하자 미출고 예정이 54L로 갱신되었다.
- 실제 불출 미리보기와 결과에 54L → 43.2kg, 밀도 0.8kg/L가 표시되고 확정 후 중복 실행 버튼이 사라졌다.
- 수기 세척 36L가 같은 제조 LOT의 서로 다른 시험번호에서 각각 14.4kg씩 차감되었다. 35L 입력은 미리보기와 불출 버튼이 비활성화되었다.
- Viewer는 BOM·생산일정을 조회할 수 있고 BOM 편집·일정 등록/수정·실제 불출 버튼은 사용할 수 없었다.
- 데스크톱 화면 배치를 확인했으며 검증용 서버·브라우저 탭은 종료했다. 기존 개발 서버는 유지했다. 일정 변경 시 완료분 보존은 DB와 HTTP 테스트로 검증했다.

원장 기능 도입 전의 엑셀 거래 내역은 별도 이력 이관 대상이다. 실제 재고 거래의 정정·취소·이동·폐기, QA 전자승인, 대시보드 집계·분석은 이번 구현 범위에 포함하지 않는다. 월 재고조사·차이 조정도 처리 정책 확인 후 추가할 범위다. 생산일정 취소는 미출고 계획만 취소한다.
